# 기획안 · 포스팅 일정 · 자동/반자동 안내 (mainmanager 전담)

이 문서는 **모든 게시물의 기획안(무슨 주제), 포스팅 일정(언제), 채널별 자동/반자동
안내(어떻게)를 한 곳에 모은 mainmanager 전담 문서**다. 이전에는 이 내용이
`content-playbook.md`·`publishing-plan.md`·`CLAUDE.md`·mainmanager 스킬 파일 자체에
조금씩 중복되어 있었는데, 여기로 통합했다. 다른 문서와의 역할 분담:

- **콘텐츠를 어떻게 만드는가**(원고 규칙·이미지 규칙·스토리보드 규칙) → `content-playbook.md`
- **자동 발행이 기술적으로 어떻게 구현됐는가**(코드 위치·자격증명·API 세부사항) → `publishing-plan.md`
- **무엇을, 언제, 자동/반자동 중 어느 방식으로 낼지, 다음 순번이 뭔지** → 이 문서
  (mainmanager가 관리하고, 사용자와의 일정/주제 확인도 이 문서 기준으로 한다)

동시에 나갔다가, 2026-09-08에 블로그만 화요일로 먼저 뺐고(검색 유입 선점), 이어서

팔로워에게 두 게시물을 동시에 내면 알고리즘 노출을 서로 갉아먹고, 카드뉴스(저장·
정독, 팔로워 대상)와 릴스(발견·확산, 비팔로워 대상)는 애초에 노출 경로가 달라
따로 낼 때 각자 확산 곡선을 온전히 갖는다**는 판단(사용자 확인, 2026-09-08). 3단계
분리는 `scripts/publish/main.py`(`--phase blog|cardnews|social|all`)와
`.github/workflows/publish.yml`(cron 3개)에 반영 완료. 반자동 채널은 콘텐츠까지만
자동 준비되고, 발행 클릭은 항상 사람이 한다. 구현 세부사항(코드·자격증명)은
`publishing-plan.md` §1 참고.

### 1-1. 발행 요일·시간을 정한 근거 (2026-09-08 SNS 시간대 조사 기반, 2026-09-13 시각 일괄 변경)

**2026-09-13, 사용자 결정으로 모든 채널의 업로드 시각을 요일은 그대로 두고 오전
10시대로 통일했다** — 아래는 원래 각 시각을 정했던 조사 근거(요일을 가르는 데
쓰인 논리는 여전히 유효하다)이고, 실제 발행 시각은 위 §1 표를 기준으로 한다.

- **카드뉴스(인스타·페이스북) — 원래 수요일 20:00, 현재 수요일 10:00**: 릴스와
  같은 날 같은 시각에 내면 같은 팔로워에게 두 게시물이 동시에 노출 경쟁을 하게
  되므로, 카드뉴스는 저장·정독 중심(팔로워 리텐션)이라 릴스의 발견·확산(비팔로워
  도달)과 굳이 같은 순간에 겹칠 이유가 없다는 "요일 분리" 논리는 그대로 유지한다
  (사용자 지적, 2026-09-08 결정). 다만 "저녁 6~11시가 SNS 참여도 최적"이라는 시간대
  자체는, 2026-09-13에 아침 일괄 배치의 단순함·일관성을 우선하기로 하면서 더 이상
  적용하지 않는다.
- **릴스·쇼츠(인스타·페이스북·유튜브쇼츠·네이버클립) — 원래 목요일 20:00, 현재
  목요일 10:00**: 인스타그램 참여도는 평일 저녁 6~11시가 가장 높고 그중 수·목요일이
  특히 강하다는 조사(Buffer 960만 게시물 분석)는 여전히 사실로 남아있지만,
  2026-09-13 사용자 결정으로 이 저녁 피크 대신 오전 10시 일괄 배치를 택했다.
  요일을 화(블로그)·수(카드뉴스)·목(릴스·쇼츠)으로 사흘에 걸쳐 분산하는 전략
  자체는 그대로 유지한다.
- **스레드 — 원래 화요일 12:30, 현재 화요일 10:15**: 스레드가 출근 직후·점심에
  도달이 강하다는 조사 근거와 무관하게 2026-09-13에 오전 10시대로 당겼다. 다만
  정확히 10:00으로는 옮길 수 없다 — 10:00 블로그 발행 직후 사람이 네이버 블로그
  URL을 기록해야만(`naver-blog-url-reminder`, 10:05 안내) 스레드가 그 링크를 채워
  게시할 수 있는 기술적 의존성이 있어, 최소 버퍼로 10:15을 유지했다(URL이 없으면
  조용히 잘못된 링크로 나가지 않고 에러로 멈춘다 — `main_thread.py`).
- **카카오톡채널 — 원래 목요일 10:30, 현재 목요일 10:00**: 카카오 비즈니스 메시지의
  야간 시간대(20:55~08:00) 발송 제한 자체는 여전히 유효하고, 10:00도 그 제한과
  무관한 안전한 시간대라 문제없이 당겼다.
- **당근마켓 — 원래 수요일 18:00, 현재 수요일 10:00**: 동네 커뮤니티 앱 특성상
  이용자가 퇴근 후 저녁 시간대에 몰린다는 조사(공식 골든타임 데이터는 아님)와
  무관하게 2026-09-13에 오전 10시로 당겼다.
- **네이버플레이스 — 원래 수요일 11:00, 현재 수요일 10:00**: 검색 기반 채널이라
  애초에 특정 골든타임의 영향이 적다고 봤던 채널이라, 오전 10시로 당기는 데
  걸리는 게 없었다.

이 표는 메인 블로그/카드뉴스/숏츠 파이프라인 채널이다. 교육뉴스(별개 파이프라인,
8채널)는 그중 구글 블로그만 같은 방식으로 완전자동이고 나머지 7채널은 반자동이다 —
§4 참고.

## 6. 결과물 보고 및 자동 진행 (2026-09-15 승인 게이트 폐지 — 완료 시 자동 진행으로 변경)

**변경 이력**: 원래는 각 단계(원고→스토리보드→렌더링→큐 등록)마다 "진행할까요?"라고
매번 물어 사용자 승인을 받는 구조였으나, 2026-09-15 사용자 지시("모든 컨텐츠는
작업이 완료된 상황을 확인하고 자동게시해줘")로 **단계 사이의 승인 게이트를
없애고, 완료가 확인되면 곧바로 다음 단계로 자동 진행**하도록 바꿨다. 실제
공개 게시(발행)는 여전히 §1·§2의 **채널별 고정 요일·시각**을 그대로 지키며,
그 시각이 되면 사용자에게 다시 묻지 않고 자동으로 나간다(§10 참고) — **없앤
것은 단계 사이의 승인 질문이지, 발행 요일 분리 전략이 아니다.**

블로그 원고(+이미지)가 완성되면:

1. mainmanager(또는 실제 작성을 수행한 세션)는 그 결과물(제목·요약·원고 링크/내용)을
   사용자에게 보고한다(보고는 계속하되, 승인을 기다리지 않는다).
2. **곧바로 `content-derivation-team` 스킬을 호출**해 카드뉴스·숏츠 스토리보드·
   채널별 캡션·스레드 초안 작성에 들어간다. 작성이 끝나면 **곧바로 이어서
   HyperFrames 렌더링까지 진행**한다 — 렌더링 착수 전 별도 확인 질문도 하지 않는다
   (`content-derivation-team/SKILL.md` §3도 동일하게 변경됨).
3. 렌더링·캡션까지 전부 끝나면 §8-2 결과 확인 체크리스트로 스스로 품질을 검증한 뒤,
   §10의 기술적 배관 체크리스트까지 통과하면 **곧바로 `queue/`(또는 `queue-edu/`)에
   등록**한다 — 네이버 블로그 URL이 아직 없어 `{{BLOG_URL}}` 치환이 안 되는 부분만
   있으면 그 부분만 보류하고 나머지는 그대로 큐에 올려둔다(§12 참고, URL이 들어오는
   즉시 자동으로 채워진다).
4. 큐에 이미 올라가 있으면 정규 cron(화=블로그, 수=카드뉴스, 목=릴스·쇼츠)이 그
   날짜·시각에 알아서 발행한다 — **콘텐츠가 그 요일보다 먼저 완성돼도 요일 자체를
   앞당기지 않는다.** 사람이 워크플로를 수동 실행해야 하는 경우(예: 예정 시각을
   지나쳤는데 아직 큐가 비어 있던 경우처럼 예외 상황)에만 §10 마지막 확인을 거쳐
   실행을 안내한다 — 정상적으로 제때 큐에 올라간 주에는 수동 실행 자체가 필요 없다.
5. 사용자가 범위를 좁히면(예: "숏츠만") 그 범위만 진행한다. 사용자가 언제든
   "잠깐 멈춰", "이번 건 확인하고 싶어" 등으로 개입하면 즉시 멈추고 그 지시를
   따른다 — 자동 진행은 기본값일 뿐 사용자의 실시간 지시보다 우선하지 않는다.

## 7. 발행 완료 후 기획안 즉시 갱신 (신설)

전달받는 즉시** 갱신한다 — 다음에 누가 물어볼 때까지 미루지 않는다. "완료된 사실"을
기록하는 것일 뿐 순번을 바꾸는 게 아니므로, §3의 "순서 변경은 항상 사용자 승인
후에만" 원칙과 별개로 승인을 기다리지 않고 바로 반영한다.

- **블로그(화요일 10:00 구글블로그 + 수요일 10:00 카드뉴스 2채널 + 목요일 10:00
  릴스·쇼츠 3채널, 완전자동 6채널, 2026-09-13부로 카드뉴스·릴스/쇼츠 시각 20:00→10:00)**:

  사라졌으면 6채널 모두(3단계 배치 전부) 발행 성공 — 즉시 `blog-calendar.md`
  "진행 상황" 절에서 해당 주차를 "완료"로 갱신하고 다음 순번을 안내한다. 폴더가
  남아있으면 `_status.json`으로 실패한 채널을 확인하거나 아직 수요일/목요일 배치를

  (2026-09-09) —
  `_status.json`의 `thread` 키로 성공 여부만 별도 확인하고, 늦어지거나 실패해도
  6채널 완료·큐 폴더 삭제에는 영향이 없다(텍스트+링크 모드로 `스레드.md`를 큐에
  올린 주에 한함 — 캐러셀 모드 주는 애초에 자동 게시 대상이 아니므로 해당 없음).

### 7-1. 매일 아침 브리핑 — 아티팩트·알림 (신설 2026-09-13)

사용자 요청("매일 내가 해야할 일을 아티팩트와 알림을 통해 알려줘")에 따라, 예약
작업 `daily-briefing`(매일 10:00 KST)이 mainmanager SKILL.md §1(작업스케쥴 관리) +
위 §2(주간 포스팅 일정) + §7(발행 완료 후 즉시 갱신) 절차를 오늘 요일에 대입해
수행하고, 그 결과를 두 가지 형태로 사용자에게 전달한다:

1. **아티팩트**: 상시 유지되는 "나인플러스 작업 현황판"
   (`https://claude.ai/code/artifact/41841cb0-d6c2-467c-ba33-4c004f60ca4d`, 고정
   링크 — 매번 같은 링크를 갱신하고 새로 만들지 않는다)을 오늘 기준으로 갱신한다 —
   승인 대기 중·사용자 액션 필요·중단된 작업·다음 브리핑 검토 항목·오늘 자동으로
   정리한 것 순으로 구성.
2. **알림**: 실제로 사용자가 오늘 처리할 것이 있을 때만(승인 대기 또는 사용자
   액션 필요 항목이 하나라도 있을 때만) PushNotification으로 핵심 1~2개를 200자
   이내로 요약해 보낸다 — 할 일이 없는 날은 알림을 보내지 않는다.

토요일은 `weekly-content-kickoff`(13:00)가 별도로 주제 확정을 진행하므로, 이 날
아침 브리핑은 상태 확인·아티팩트 갱신까지만 하고 주제 확정 절차 자체는 수행하지
않는다.
- **캡션 삽입 확인 (2026-09-11 신설)**: 카드뉴스·릴스·쇼츠 발행을 "완료"로 보고할
  때는 `_status.json`의 `done: true`만 보고 끝내지 않는다. `scripts/publish/main.py`의
  `_require_caption()`(2026-09-11 신설)이 캡션이 빈 문자열이면 발행 자체를 막고
  에러로 남기므로, 지금은 `done: true`면 캡션도 실제로 채워져서 나갔다는 뜻이지만
  — 36주차에 캡션이 빈 채로 조용히 "성공" 처리된 실사고가 있었으니, 보고할 때
  "캡션 포함 발행 완료"처럼 캡션 상태를 명시적으로 언급한다. 유튜브 쇼츠의
  **고정댓글은 자동화 대상이 아니다** — `scripts/publish/youtube.py`는 영상
  업로드만 하고 댓글 작성·고정은 API로 처리하지 않으므로, "📌 고정댓글을
  참고해주세요" 온스크린 CTA를 쓰는 주는 매번 사용자가 유튜브 앱에서 직접 댓글을
  달고 고정해야 한다는 점을 완료 보고 때 함께 안내한다.

## 8. 다른 에이전트 작업지시 및 결과 확인 (신설, 2026-09-07)

## 10. 자동게시 전 품질 검토 (신설, 2026-09-07)

완전자동 채널(메인 블로그 4채널, 교육뉴스 구글 블로그)을 **`queue/`·`queue-edu/`에
올리기 직전** 반드시 아래 검토를 거친다 — 이 검토가 §6의 "자동 진행" 전 마지막
품질 관문이다(2026-09-15부터 검토 통과 = 큐 등록, 별도로 사람에게 "발행할까요?"를
묻지 않는다).

1. **맞춤법·띄어쓰기 검토**: 큐에 올라간 최종 원고(제목·본문·표·캡션 전체)를 처음부터
   끝까지 다시 훑어 오탈자·띄어쓰기 오류를 찾는다. 발견하면 큐 파일과 로컬 원본
   양쪽을 함께 수정한다.
2. **정보의 사실성 검토**: 날짜·수치·기관명·인용문·출처 링크가 실제 사실과 일치하는지,
   원고 작성 시점 이후 상황이 바뀐 건 없는지(예: 일정 변경, 수치 갱신) 재확인한다.
   의심스러운 항목은 재검색해서 교차 확인한다.
3. **기술적 배관(plumbing) 체크리스트** (2026-09-09 신설 — 36주차 실사고 재발 방지):
   과거 이 항목들을 놓쳐 실제로 빈 채로/잘못된 링크로 게시된 적이 있어 매번 명시
   확인한다.
   - `구글블로그용.md` 프런트매터에 `title`·`labels`·`search_description` 셋 다
     채워져 있는지(HTML 주석으로만 적어두면 파서가 읽지 않아 빈 채로 게시된다).
     `labels`는 SNS 해시태그가 아니라 블로그 상단 메뉴 카테고리 **정확히 1개**인지.
   - 본문의 `<img src="[사진 자리 N · 설명]">` 플레이스홀더 "설명"이 같은 폴더
     실제 이미지 파일명(공백 제거 후)과 정확히 일치하는지 — 안 맞으면 그 이미지
     자리만 조용히 깨진 채로 게시된다(`fill_image_placeholders()`는 실패해도
     발행을 막지 않고 경고만 남긴다).
   - 그 주 네이버 블로그가 이미 발행되어 `python scripts/publish/set_naver_url.py
     <URL>`로 `_status.json`의 `naver_blog_url`이 기록되어 있는지 — 안 되어 있으면
     카드뉴스/숏츠 캡션과 화요일 스레드의 `{{BLOG_URL}}`이 전부 구글 블로그(SEO용
     미러) 주소로 대신 채워진다.
   - 화요일 10:15 스레드를 자동 게시할 계획이면(텍스트+링크 모드) `스레드.md`가

   - KittyChat 댓글→DM 자동화가 "전체" 모드로 켜져 있는지(§4 CTA 문구가 이 전제로
     쓰였는데, "선택" 모드로 바뀌어 있으면 안내만 하고 실제로는 응답이 안 나간다 —
     한 번 확인했다고 끝내지 말고 온스크린 CTA를 새로 확정할 때마다 재확인).
   - `카드뉴스/채널별_캡션.md`·`숏츠/채널별_캡션.md`의 작성자용 메모가 정확히

     `parse_caption_sections()`가 발행 시 자동으로 걸러낸다. 다른 형식으로 적으면
     그대로 게시된다(36주차 카드뉴스에서 실제로 발생 — 2026-09-09 파서 수정 완료,

   순서가 안 된 채널까지 한꺼번에 나가버리는 실사고가 난다(2026-09-15 8주차 실제
   발생 — 카드뉴스·릴스·쇼츠가 예정보다 이틀·사흘 앞당겨 나갔다가 사용자가 직접
   삭제하고 `_status.json`을 초기화해 정규 요일로 되돌림).

## 11. 작업순서 인지 지원 — mainmanager의 핵심 임무 (신설 2026-09-13, 2026-09-15 §6 변경에 맞춰 갱신)

사용자가 블로그·교육뉴스를 **토요일에 미리 작업하는 이유는 화·수·목 게시
일정(§1·§2)에 지장을 주지 않기 위해서**다. mainmanager의 핵심 임무 중 하나는
"지금 무슨 단계이고, 다음에 뭘 했는지"를 사용자가 항상 인지할 수 있게 지원하는
것이다 — 단순히 상태를 조회해서 답하는 것을 넘어, 능동적으로 진행 상황을 알린다.

1. **자동 다음 단계 진행(2026-09-15 변경)**: 블로그 원고(+이미지)나 교육뉴스 10개
   파일 작업이 끝났다고 판단되면(§5·education-news-team §4), §6 원칙대로 **승인을
   묻지 않고 곧바로** 카드뉴스·숏츠 스토리보드→렌더링→큐 등록까지 이어서
   진행하고, 단계가 끝날 때마다 "무엇을 완료했는지"를 짧게 보고한다 — 사용자가
   먼저 물어볼 때까지 기다리지 않는다.
2. **아티팩트로 워크플로 체크 제공(이 프로젝트 한정)**: 이 프로젝트에서 작업
   순서나 파이프라인 진행 상태를 안내할 때는 채팅 텍스트로만 설명하지 않고,
   **항상 아티팩트**로 현재 단계·다음 단계·막혀 있는 지점(예: URL 대기 등)을
   한눈에 볼 수 있게 띄운다. 매번 새 아티팩트를 만들지 않고, 기존 아티팩트(예:
   "나인플러스 작업 현황판" — 그날의 할 일, "발행 파이프라인 점검" — 진행 중인
   콘텐츠의 단계별 체크리스트, "주간 콘텐츠 리듬" — 매주 반복되는 요일별 일정)를
   상황에 맞게 골라 같은 링크에 갱신한다.
3. 이 원칙은 §7-1(매일 아침 브리핑)·§8(다른 에이전트 작업지시)과 함께 적용된다 —
   §6·§10에서 단계 사이 승인 게이트는 없앴지만, 실제 공개 게시가 나가는 정규
   요일·시각(§1·§2)은 그대로 지키므로, 그 사실을 사용자가 항상 알 수 있게 안내하는
   역할은 오히려 더 중요해졌다.

## 12. 블로그 URL 입력 시 자동 캡션·설명글 업데이트 (신설 2026-09-15)

사용자가 채팅에 네이버 블로그 글 주소(`blog.naver.com/...`)를 붙여넣으면, 어느
파이프라인 것인지 스스로 판단해 **묻지 않고 곧바로** 기록한다:

1. 직전 대화 맥락(어떤 주차/호를 작업 중이었는지)과 사용자의 표현("교육뉴스
   URL이야" 등)으로 **메인 블로그**인지 **교육뉴스**인지 판단한다. 애매하면 짧게
   확인만 하고(예: "메인 블로그 URL 맞으실까요?"), 명확하면 바로 진행한다.
2. **메인 블로그**면 저장소 루트에서
   `python scripts/publish/set_naver_url.py <URL>`을 실행한다 — `queue/` 아래
   처리 중인 폴더의 `_status.json`에 `naver_blog_url`로 기록되며, 이후 카드뉴스·
   숏츠 캡션과 스레드의 `{{BLOG_URL}}`이 정규 발행 시점에 이 값으로 자동
   치환된다(사람이 캡션 파일을 직접 고칠 필요 없음 — 플레이스홀더 방식이 이미
   "자동 업데이트"다).
3. **교육뉴스**면 `python scripts/publish/set_naver_url.py --edu <URL>`을
   실행한다 — `queue/_edu_thread_link.json`에 기록되며, 목요일 `edu-thread-reminder`가
   이 값을 읽어 스레드 초안을 만든다.
4. 실행 후 기록된 내용을 커밋·푸시하고, 무엇을 어디에 기록했는지 한 줄로 확인해준다.
5. 이 프로세스는 §6의 "완료 시 자동 진행" 원칙과 같은 맥락이다 — URL이 들어오는
   시점에 곧바로 처리하고, 실제 게시는 여전히 정규 요일에 이뤄진다.
