# 기획안 · 포스팅 일정 · 자동/반자동 안내 (mainmanager 전담)

이 문서는 **모든 게시물의 기획안(무슨 주제), 포스팅 일정(언제), 채널별 자동/반자동
안내(어떻게)를 한 곳에 모은 mainmanager 전담 문서**다. 이전에는 이 내용이
`content-playbook.md`·`publishing-plan.md`·`CLAUDE.md`·mainmanager 스킬 파일 자체에
조금씩 중복되어 있었는데, 여기로 통합했다. 다른 문서와의 역할 분담:

- **콘텐츠를 어떻게 만드는가**(원고 규칙·이미지 규칙·스토리보드 규칙) → `content-playbook.md`
- **자동 발행이 기술적으로 어떻게 구현됐는가**(코드 위치·자격증명·API 세부사항) → `publishing-plan.md`
- **무엇을, 언제, 자동/반자동 중 어느 방식으로 낼지, 다음 순번이 뭔지** → 이 문서
  (mainmanager가 관리하고, 사용자와의 일정/주제 확인도 이 문서 기준으로 한다)

완전자동 채널은 GitHub Actions가 API를 직접 호출해 발행하므로 사람이 로그인할
필요가 없다. **2026-09-09부로 발행이 3단계로 나뉜다** — 구글 블로그(화 10:00) →
카드뉴스 캐러셀(수 20:00) → 릴스·쇼츠(목 20:00). 예전에는 4채널이 목요일 09:00에
동시에 나갔다가, 2026-09-08에 블로그만 화요일로 먼저 뺐고(검색 유입 선점), 이어서
2026-09-09에 카드뉴스와 릴스/쇼츠도 다시 하루씩 갈랐다 — **같은 계정이 같은 날 같은
팔로워에게 두 게시물을 동시에 내면 알고리즘 노출을 서로 갉아먹고, 카드뉴스(저장·
정독, 팔로워 대상)와 릴스(발견·확산, 비팔로워 대상)는 애초에 노출 경로가 달라
따로 낼 때 각자 확산 곡선을 온전히 갖는다**는 판단(사용자 확인, 2026-09-08). 3단계
분리는 `scripts/publish/main.py`(`--phase blog|cardnews|social|all`)와
`.github/workflows/publish.yml`(cron 3개)에 반영 완료. 반자동 채널은 콘텐츠까지만
자동 준비되고, 발행 클릭은 항상 사람이 한다. 구현 세부사항(코드·자격증명)은
`publishing-plan.md` §1 참고.

### 1-1. 발행 요일·시간을 정한 근거 (2026-09-08 SNS 시간대 조사 기반)

- **카드뉴스(인스타·페이스북) — 수요일 20:00**: 릴스와 같은 날 같은 시각에 내면
  같은 팔로워에게 두 게시물이 동시에 노출 경쟁을 하게 되고, 카드뉴스는 저장·정독
  중심(팔로워 리텐션)이라 릴스의 발견·확산(비팔로워 도달)과 굳이 같은 순간에 겹칠
  이유가 없다(사용자 지적, 2026-09-08 결정). 수요일 저녁도 아래와 같은 "저녁
  6~11시·수·목요일 강세" 데이터 범위 안이라 새 가정을 추가하지 않고 그대로
  하루 앞당겨 썼다.
- **릴스·쇼츠(인스타·페이스북·유튜브쇼츠·네이버클립) — 목요일 20:00**: 인스타그램
  참여도는 평일 저녁 6~11시가 가장 높고 그중 수·목요일이 특히 강하다(Buffer 960만
  게시물 분석). 릴스·쇼츠도 동일하게 저녁 7~10시대가 최적이라는 데이터가 일관되게
  나온다. 블로그(화 오전)로 검색 유입을 먼저 잡고, 수요일 저녁 카드뉴스, 목요일
  저녁 릴스로 한 주 동안 노출 시점을 세 갈래로 분산시키는 전략이다.
- **스레드 — 화요일 12:30**: 스레드는 출근 직후(8~9시)와 점심(12~1시) 도달이 강하다.
  블로그가 나가는 당일 점심에 링크형 스레드로 바로 트래픽을 유도한다.
- **카카오톡채널 — 목요일 10:30**: 카카오 비즈니스 메시지는 야간 시간대(20:55~08:00)
  발송이 제한되므로 오전이 안전하다. 릴스·쇼츠가 나가는 목요일 당일 오전에 예고
  성격으로 배치했다.
- **당근마켓 — 수요일 18:00**: 동네 커뮤니티 앱 특성상 이용자가 퇴근 후 저녁 시간대에
  몰린다는 것이 일반적으로 알려져 있다(공식 골든타임 데이터는 없음). 카드뉴스(수
  20:00)보다 앞선 시각이라 겹치지 않는다.
- **네이버플레이스 — 수요일 11:00**: 검색 기반 채널이라 특정 골든타임의 영향이
  적다 — 꾸준히 올리는 것이 시간대보다 중요해서 평일 오전으로 고정했다.

이 표는 메인 블로그/카드뉴스/숏츠 파이프라인 채널이다. 교육뉴스(별개 파이프라인,
8채널)는 그중 구글 블로그만 같은 방식으로 완전자동이고 나머지 7채널은 반자동이다 —
§4 참고.

지금까지 다룬 주제, 다음 호 후보, 운영 원칙은 **[docs/education-news-log.md](education-news-log.md)**

실제 주제 조사·10개 파일 작성·큐 등록은 **`education-news-team` 스킬**이 mainmanager의
지시를 받아 수행한다(§8-1 트리거 표 참고, 2026-09-08부로 기존 계정 레벨 스킬
`education-news-weekly` 대체). 전 채널 CTA·법정고시사항 없이 해시태그로만 블로그
유입을 간접 유도하는 방침은 `docs/education-news-publishing.md`를 따른다.

## 5. 토요일 주제 확정 절차 (신설, 2026-09-08 토요일 13:00으로 변경)

매주 토요일 13:00 브리핑(예약 작업 `weekly-content-kickoff`가 트리거)에서 mainmanager는:

1. `docs/blog-calendar.md`에서 이번 주 예정 주제(다음 순번)를, `docs/education-news-log.md`에서
   교육뉴스 다음 호 후보(유력 1건)를 각각 확인해 사용자에게 제시한다.
2. "이대로 진행할까요, 아니면 더 나은 주제를 검색해볼까요?" 라고 물어 확인을 받는다.
3. 사용자가 "그대로 진행"이라고 하면 그 주제로 바로 원고/큐레이션 작성에 들어간다.
4. 사용자가 "다른 주제를 찾아봐" 등으로 요청하면, 최신 뉴스·입시 일정을 검색해 2~4개
   대안 후보를 요약과 함께 제시하고 사용자의 선택을 기다린다 — mainmanager가 임의로
   주제를 확정하지 않는다.
5. 최종 확정된 주제만 `docs/blog-calendar.md`(순서 변경 시) 또는
   `docs/education-news-log.md`(다음 호 후보 갱신 시)에 반영한다.

## 6. 결과물 보고 및 승인 게이트 (신설)

블로그 원고(+이미지)가 완성되면:

1. mainmanager(또는 실제 작성을 수행한 세션)는 그 결과물(제목·요약·원고 링크/내용)을
   사용자에게 보고한다.
2. "카드뉴스·숏츠 스토리보드 작성으로 진행할까요?"라고 물어 승인을 받는다
   (`content-playbook.md` §0의 워크플로 규칙과 동일한 게이트). 승인 후 실제 작성은
   `content-derivation-team` 스킬이 이어받는다 — 스토리보드·캡션·스레드 작성 후
   렌더링(HyperFrames) 착수 전에 다시 한번 사용자 확인을 받는다(2단계 승인 게이트).
3. **사용자 승인이 없으면 다음 과정(카드뉴스/숏츠 스토리보드 착수)으로 진행하지
   않는다.** 승인이 늦어지거나 없으면 그 상태로 대기하고, 다음 브리핑 때 "승인
   대기중"으로 안내한다.
4. 사용자가 범위를 좁히면(예: "숏츠만") 그 범위만 진행한다.

## 7. 발행 완료 후 기획안 즉시 갱신 (신설)

`blog-calendar.md`·`education-news-log.md`는 **발행이 실제로 끝난 걸 확인하거나
전달받는 즉시** 갱신한다 — 다음에 누가 물어볼 때까지 미루지 않는다. "완료된 사실"을
기록하는 것일 뿐 순번을 바꾸는 게 아니므로, §3의 "순서 변경은 항상 사용자 승인
후에만" 원칙과 별개로 승인을 기다리지 않고 바로 반영한다.

- **블로그(화요일 10:00 구글블로그 + 수요일 20:00 카드뉴스 2채널 + 목요일 20:00
  릴스·쇼츠 3채널, 완전자동 6채널)**: `queue/` 폴더를 확인한다. 그 주 폴더가
  사라졌으면 6채널 모두(3단계 배치 전부) 발행 성공 — 즉시 `blog-calendar.md`
  "진행 상황" 절에서 해당 주차를 "완료"로 갱신하고 다음 순번을 안내한다. 폴더가
  남아있으면 `_status.json`으로 실패한 채널을 확인하거나 아직 수요일/목요일 배치를
  기다리는 중인지 보고하고, 완료 처리하지 않는다. **스레드(화요일 12:30, 7번째
  완전자동 채널)는 이 6채널 완료 판정과 별개로 독립 운영된다**(2026-09-09) —
  `_status.json`의 `thread` 키로 성공 여부만 별도 확인하고, 늦어지거나 실패해도
  6채널 완료·큐 폴더 삭제에는 영향이 없다(텍스트+링크 모드로 `스레드.md`를 큐에
  올린 주에 한함 — 캐러셀 모드 주는 애초에 자동 게시 대상이 아니므로 해당 없음).
- **교육뉴스(매주 화요일 10:00, 별개 파이프라인)**: `queue-edu/` 폴더를 확인한다. 그 주
  폴더가 있다가 사라졌으면 구글 블로그 발행에 성공했다는 뜻 — 즉시
  `education-news-log.md`를 갱신한다(다룬 주제를 "지금까지 다룬 주제" 표에 추가하고
  "다음 호 후보"에서 제거/갱신). 폴더가 처음부터 없었다면(사용자가 queue-edu 자동
  발행을 안 쓰고 8채널 모두 수동으로 진행한 주라면) 이 방법으로는 감지할 수 없으므로,
  사용자가 발행 완료를 알려주면 그때 갱신한다.
- 매일 아침 자동 브리핑에서도 이 확인·갱신을 수행한다. 특히 금요일 브리핑은 전날
  (목요일) 블로그 발행 결과를, 월요일 이후 브리핑은 그 주 교육뉴스 `queue-edu/` 상태를
  확인하기 좋은 시점이므로, 비어 있으면 그 자리에서 해당 문서를 갱신하고 커밋한다.

## 8. 다른 에이전트 작업지시 및 결과 확인 (신설, 2026-09-07)

§6이 "상태를 조회해서 보여주는" 수동적 역할이라면, 이 절은 mainmanager가 조건이
갖춰지면 **직접 해당 에이전트를 호출해 작업을 지시**하고, 결과물이 돌아오면 **정해진
기준으로 확인**한 뒤에만 완료로 처리하는 능동적 역할이다.

### 8-1. 언제 어떤 에이전트를 호출하는지

| 트리거 | 호출 대상 | 무엇을 지시하는지 |
|---|---|---|
| §5 승인 게이트 통과("카드뉴스·숏츠 진행할까요?"에 승인) | content-derivation-team | 승인된 블로그 원고 폴더 경로 + 범위(전체/숏츠만 등) |
| 블로그 사진 자리가 확정(실사진 저장 또는 일러스트 방향 결정)되어 실제 오버레이/일러스트 산출물이 필요할 때 | design_team | 사진 자리 번호, 실사진 경로 또는 일러스트 프롬프트, 저장 위치 |
| §5 토요일 주제 확정 후, 교육뉴스 다음 호 주제가 확정됐을 때 | education-news-team | 확정된 주제 요약(사용자가 그대로 진행/다른 주제 검색 중 어느 쪽이었는지 포함) |
| 교육뉴스 다음 호 후보만 미리 조사가 필요할 때(주제 미확정) | education-news-team | "후보만 조사"라고 범위를 명시 — 이 경우 원고 작성(§2)까지 진행하지 않고 후보만 보고 |
| `docs/algorithm-search-log.md` 최신 항목이 28일 이상 지났거나 사용자가 명시 요청 | algorithm-searching-team | (특별한 지시 없이 호출만 — 이 스킬이 스스로 조사 범위를 판단) |
| 사용자가 §7(별도 작업)을 지시 | 해당 작업에 맞는 에이전트 | 범위를 좁혀 말한 그대로 전달 |

호출은 Skill 도구로 대상 에이전트를 직접 실행한다(사용자가 매번 다시 슬래시 명령을
치지 않아도 되게). 호출 시 그 에이전트가 스스로 판단하기 어려운 맥락(승인 여부,
확정된 주제/범위, 관련 파일 경로)을 반드시 함께 전달한다.

### 8-2. 결과 확인 체크리스트

에이전트가 결과물을 내놓으면, 사용자에게 "완료됐다"고 보고하기 전에 아래 기준으로
스스로 확인한다. 기준을 벗어나면 완료 처리하지 않고 무엇이 어긋났는지 구체적으로
적어 재작업을 요청하거나(가능한 경우) 사용자에게 판단을 넘긴다.

- **content-derivation-team 결과**: 카드뉴스 스토리보드가 9~10장·1080×1350 규격인지,
  숏츠가 20~30초·6~7장면인지, 온스크린 CTA가 3회(오프닝·중반·클로징) 표시돼 있는지,
  "확인이 필요한 부분" 섹션이 존재하는지(`content-playbook.md` §5~§7).
- **design_team 결과**: 팔레트가 남색(#10203f)+골드(#F0B93D)+흰색만 쓰였는지, 규격이
  1080×1080인지, 얼굴·실명이 있는 실사진이면 모자이크가 됐는지(§3, §12).
- **algorithm-searching-team 결과**: 지침을 실제로 바꿨다면 PR 형태로 올라왔는지,
  변경 근거에 출처 URL이 최소 2개 이상 달려 있는지.
- **education-news-team 결과**: 마스터본 3종(마크다운·구글블로그 HTML·밴드용)+채널별
  배포본 5종(유튜브설명란·유튜브커뮤니티·당근·네이버플레이스·카카오톡)+업로드체크리스트
  1종+삽화 1장, 총 10개 파일이 모두 존재하는지, `발행이력.md`와 중복되지 않는 주제인지,
  전 채널(카카오톡 포함) CTA·법정고시사항 없이 해시태그만 들어갔는지(§4 CTA 방침과는
  별개 — 교육뉴스는 순수 정보성 유지, `education-news-team/SKILL.md` §3 참고).
- 위 §1(광고 컴플라이언스)의 실적/경력 과장 체크리스트도 홍보형(P) 콘텐츠 결과물을
  확인할 때 함께 적용한다.

### 8-3. 사용자 보고

확인이 끝나면 "무엇을 지시했고, 결과가 기준을 통과했는지"를 한 줄로 요약해 보고한다.
기준 미달이면 통과 못 한 항목을 구체적으로 짚어서 알린다 — "완료했습니다"로 뭉뚱그려
보고하지 않는다.

## 10. 자동게시 전 품질 검토 (신설, 2026-09-07)

완전자동 채널(메인 블로그 4채널, 교육뉴스 구글 블로그)에 **실제로 게시 트리거를
당기기 직전**(= `queue/`·`queue-edu/`에 콘텐츠를 올린 뒤, 사용자에게 워크플로 실행을
요청하거나 예약 시각을 기다리는 시점) 반드시 아래 검토를 거친다. 이건 §5/§6의
"발행 승인 게이트"(이 콘텐츠로 발행해도 되는지)와는 별개의 **마지막 체크포인트**다.

1. **맞춤법·띄어쓰기 검토**: 큐에 올라간 최종 원고(제목·본문·표·캡션 전체)를 처음부터
   끝까지 다시 훑어 오탈자·띄어쓰기 오류를 찾는다. 발견하면 큐 파일과 로컬 원본
   양쪽을 함께 수정한다.
2. **정보의 사실성 검토**: 날짜·수치·기관명·인용문·출처 링크가 실제 사실과 일치하는지,
   원고 작성 시점 이후 상황이 바뀐 건 없는지(예: 일정 변경, 수치 갱신) 재확인한다.
   의심스러운 항목은 재검색해서 교차 확인한다.
3. **기술적 배관(plumbing) 체크리스트** (2026-09-09 신설 — 36주차 실사고 재발 방지):
   과거 이 항목들을 놓쳐 실제로 빈 채로/잘못된 링크로 게시된 적이 있어 매번 명시
   확인한다.
   - `구글블로그용.md` 프런트매터에 `title`·`labels`·`search_description` 셋 다
     채워져 있는지(HTML 주석으로만 적어두면 파서가 읽지 않아 빈 채로 게시된다).
     `labels`는 SNS 해시태그가 아니라 블로그 상단 메뉴 카테고리 **정확히 1개**인지.
   - 본문의 `<img src="[사진 자리 N · 설명]">` 플레이스홀더 "설명"이 같은 폴더
     실제 이미지 파일명(공백 제거 후)과 정확히 일치하는지 — 안 맞으면 그 이미지
     자리만 조용히 깨진 채로 게시된다(`fill_image_placeholders()`는 실패해도
     발행을 막지 않고 경고만 남긴다).
   - 그 주 네이버 블로그가 이미 발행되어 `python scripts/publish/set_naver_url.py
     <URL>`로 `_status.json`의 `naver_blog_url`이 기록되어 있는지 — 안 되어 있으면
     카드뉴스/숏츠 캡션과 화요일 스레드의 `{{BLOG_URL}}`이 전부 구글 블로그(SEO용
     미러) 주소로 대신 채워진다.
   - 화요일 12:30 스레드를 자동 게시할 계획이면(텍스트+링크 모드) `스레드.md`가
     큐 폴더에 실제로 올라가 있는지, `{{BLOG_URL}}` 줄이 통째로 빠지지 않았는지.
   - KittyChat 댓글→DM 자동화가 "전체" 모드로 켜져 있는지(§4 CTA 문구가 이 전제로
     쓰였는데, "선택" 모드로 바뀌어 있으면 안내만 하고 실제로는 응답이 안 나간다 —
     한 번 확인했다고 끝내지 말고 온스크린 CTA를 새로 확정할 때마다 재확인).
4. 수정한 내용이 있으면 무엇을 고쳤는지 사용자에게 짧게 보고한다.
5. **검토가 끝나면 "자동게시를 시작할까요?"라고 명시적으로 물어보고, 사용자 승인
   후에만** 다음 단계(워크플로 실행 요청/안내, 또는 예약 발행 확정)로 진행한다 —
   검토했다고 해서 이 마지막 확인을 생략하지 않는다.
