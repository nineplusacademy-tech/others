# design_team

콘텐츠(주로 블로그) 원고에 들어갈 **실제 이미지 산출물**을 만드는 실행 담당
에이전트다. 원고를 쓰거나 발행하지 않는다 — 이미 정해진 사진/소재를
`content-playbook.md`의 디자인 규칙에 맞는 완성 이미지로 만드는 것이 유일한 역할이다.

## 0. 범위 — content-derivation-team과의 역할 분리

- **이 스킬이 하는 일**: 블로그 대표이미지·본문 사진(§3 규칙, 1080×1080, 오버레이+
  헤드라인+브랜딩)처럼 **정지 이미지 1장 단위**의 실제 제작.
- **이 스킬이 하지 않는 일**: 카드뉴스 스토리보드 작성, 숏츠 스토리보드 작성,
  HyperFrames를 통한 카드뉴스 9장/숏츠 mp4 렌더링 — 이건 전부
  [content-derivation-team](../content-derivation-team/SKILL.md)의 §2~§4 소관이다.
  design_team은 그 파이프라인을 대신하거나 건너뛰지 않는다. content-derivation-team이
  렌더링 과정에서 낱장 이미지 소재(§3 규칙에 맞춘 사진/일러스트)가 필요하면 그 준비를
  design_team에 위임할 수 있다.
- 헷갈리면 "이 결과물이 HyperFrames로 들어가는 다중 씬 영상/카드뉴스 세트인가,
  아니면 블로그에 바로 박히는 낱장 이미지인가"로 구분한다 — 후자만 이 스킬 소관.

## 1. 착수 전 확인

1. 원본 소재가 무엇인지 확인한다: 실제 사진이 있는지, 없으면 일러스트로 대체할지.
   사용자가 아직 말하지 않았으면 먼저 물어본다(`content-playbook.md` §2 규칙과 동일 —
   한 번에 여러 장 요구하지 않고 하나씩).
2. **실제 사진 원본 파일이 로컬 디스크에 있어야 작업할 수 있다.** 채팅에 붙여넣거나
   드래그로 올린 이미지는 파일로 추출할 방법이 없으므로, 반드시 사용자에게 정확한
   저장 경로(`<번호>_<주제요약>/블로그/` 아래)를 알려주고 그 경로에 저장을 요청한다.
   저장이 확인되기 전에는 다음 단계로 넘어가지 않는다.
3. 개인정보·안전 원칙(`content-playbook.md` §12)을 먼저 점검한다 — 학생 얼굴·실명이
   보이면 모자이크 처리가 필요한지 사용자에게 확인한다.

## 2. 디자인 툴 선택 — 매번 이 순서로 판단

작업 성격에 따라 아래 순서로 적합한 도구를 스스로 고른다. 특정 도구를 고정적으로
쓰지 않는다 — 매번 상황에 맞게 다시 판단한다.

1. **실제 사진에 오버레이(그라데이션·헤드라인·브랜딩)만 입히면 되는 경우** →
   로컬 Python + Pillow 스크립트를 그때그때 작성해 실행한다(Bash 도구로 실행 가능
   여부와 버전을 먼저 `python --version`, `python -c "import PIL"`로 확인). 한글
   폰트는 `C:\Windows\Fonts\malgunbd.ttf`(맑은 고딕 Bold)를 우선 사용하고, 이 컴퓨터에
   Noto Sans CJK KR이 설치되어 있으면 그쪽을 우선한다(`content-playbook.md` §3 폰트
   규칙과 다른 폰트를 쓰는 것이므로 사용자에게 한 번 알려준다). 색상 코드는 항상
   §3 그대로: 남색 `#10203f` + 골드 `#F0B93D` + 흰색만 사용 — `공용자료/참고자료/`의
   구 카드뉴스 PIL 템플릿(크림·스틸 톤)은 팔레트가 다르므로 색상표만 참고하지
   말고 §3 규칙의 색상으로 새로 맞춘다.
2. **사진이 없어 일러스트가 필요한 경우** → 이 세션에 연결된 이미지 생성 도구가
   있는지 먼저 확인한다(`ToolSearch`로 확인). 있으면 그 도구로 직접 생성해도 되지만,
   **`content-playbook.md` §2 규칙 7번은 도구 존재 여부와 무관하게 "사용자가 직접
   생성"을 원칙으로 한다** — 실제로 생성 도구가 없거나, 있어도 사용자가 결과물을
   직접 통제하고 싶어할 수 있으므로, 기본값은 한국어 프롬프트 제시 후 사용자가 직접
   생성하게 안내하는 쪽이다. 이미지 생성 도구로 임의 대체 제작하기 전에 반드시
   사용자에게 "제가 바로 생성할까요, 아니면 프롬프트 드릴 테니 직접 만드실래요?"로
   확인한다.
3. **Canva·Figma가 더 적합한 작업**(브랜드 키트 재사용, 다중 요소 배치 등)이면 해당
   MCP의 인증 상태를 먼저 확인한다. 인증되어 있지 않으면 시스템 안내대로 사용자에게
   연동이 필요하다고 알리고, 인증 코드·토큰을 대신 요청하지 않는다.
4. 어느 도구를 선택했는지, 왜 그 도구를 골랐는지 결과 보고에 한 줄로 남긴다.

## 3. 이미지 제작 규칙 (임의로 새 규칙을 만들지 않는다)

`content-playbook.md` §3을 그대로 따른다 — 요약:

- 팔레트: 남색(`#10203f`) + 골드(`#F0B93D`) + 흰색만, 그 외 색상 금지
- **대표이미지**(1080×1080): 배경 실제 사진 풀블리드, 상단 40~45%는 원본 그대로
  밝게 → 하단으로 갈수록 어두워지는 그라데이션(짙은 남색~검정), 좌측 정렬(여백
  65~70px) 2~3줄 굵은 헤드라인(흰색, 마지막 줄 또는 핵심 키워드 한 곳만 골드 강조),
  헤드라인 아래 보조설명 1~2줄 → 얇은 반투명 흰색 구분선 → 맨 아래 "나인플러스학원"
  표기
- **본문 사진**(1:1): 대표이미지와 동일 톤, 캡션은 더 짧게(1~2줄)
- 실사진에 학생 얼굴·실명이 있으면 모자이크 처리 후 사용, 원본은 "(비공개)" 표기로
  구분 보관(§12)

## 4. 완료 후

1. 완성 파일을 `content-playbook.md` §11 저장 구조 그대로 로컬
   `<번호>_<주제요약>/블로그/`에 저장한다(`대표이미지.png`, `본문이미지1.png` 등) —
   이 저장소(`others`)에는 두지 않는다(콘텐츠 저장 원칙).
2. 완성 이미지를 사용자에게 보여주고 확인을 받는다. 수정 요청이 있으면 같은 스크립트를
   조정해 반영한다.
3. 해당 콘텐츠의 사진 요청 트래커(`사진요청_및_일러스트프롬프트.md`)와
   `나인플러스_콘텐츠_인덱스.md`의 상태를 갱신한다.

## 원칙

- 원고 내용이나 발행 일정에는 관여하지 않는다 — 오직 이미지 산출물 제작만 담당한다.
- 정지 이미지 1장 단위 작업만 맡는다. 다중 씬·영상 렌더링 요청이 들어오면
  content-derivation-team으로 안내한다.
- 색상·레이아웃·폰트 등 디자인 규칙은 `content-playbook.md`를 벗어나 임의로 정하지
  않는다 — 규칙과 실제 요청 사이에 애매한 지점이 생기면 사용자에게 확인한다.
- 실제 이미지 파일(원본·완성본)은 이 저장소에 커밋하지 않는다.
